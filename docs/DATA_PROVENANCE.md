# Data Provenance

## Public-data policy

Every input and example committed to this repository must be purpose-built synthetic data. "Synthetic" means created for software demonstration or verification without copying, transforming, perturbing, aggregating, reverse-engineering, or calibrating against a real customer's facility, tender, drawing, asset register, telemetry, incident, or operating procedure.

Changing names or applying a scale factor does not make real data synthetic.

The public contracts require `data_classification` to equal `synthetic`. That field is an enforceable application boundary, but it is not proof of origin. Human provenance review remains mandatory.

## Published dataset inventory

| Artifact | Classification | Creation method | Intended use |
|---|---|---|---|
| `examples/synthetic/reference-2n.snapshot.json` | Synthetic | Fictional 2 MW A/B topology constructed from round values and explicit simplifying assumptions | Topology, capacity, transfer, and UPS-energy verification |
| `healthy.scenario.json` | Synthetic | Empty event sequence over the reference horizon | Baseline and determinism verification |
| `generator-success.scenario.json` | Synthetic | Purpose-built PDU B maintenance, path A utility loss, 15-second UPS bridge, and successful generator sequence | Ride-through and generator-state verification |
| `composite-failure.scenario.json` | Synthetic | Purpose-built event timing selected to create independently calculable battery and interruption boundaries | Derived alarms, depletion, outage, recovery, and energy-metric verification |
| `expected/reference-metrics.json` | Synthetic | Manual transcription of the independent equations in `REFERENCE_SCENARIO.md`; never generated by the engine | Acceptance oracle and reconciliation evidence |

No published telemetry file is an observation. API telemetry is a protocol-neutral, SCADA-style point series deterministically generated from simulation state and labeled `quality=synthetic` on every row. It is not a Modbus capture, register map, or export from an operational system.

## Reference-fixture construction

The reference topology uses two 2 MW paths, two 800 kW fictional dual-cord loads, and two UPS units with exactly 120 kWh of modeled usable energy. These round values were chosen so millijoule arithmetic and event boundaries can be calculated independently. In the composite case, path B enters maintenance at 62,000 ms, utility A fails at 120,000 ms, and UPS A then supplies 1.6 MW. The event times establish a low-energy boundary at 336,000 ms, depletion at 390,000 ms, and a 32,000 ms interruption before path B recovery.

The independent derivation is in [Reference Scenario](REFERENCE_SCENARIO.md). It is the provenance record for expected values and must be updated whenever a fixture changes.

## Lineage and hashes

At run time, the system:

1. rejects ambiguous or non-finite JSON;
2. validates the exact versioned contract and semantic references;
3. canonicalizes the original snapshot and scenario independently;
4. records their SHA-256 hashes in the result;
5. computes state hashes throughout the timeline; and
6. records a computation hash over the deterministic semantic result.

Hashes support traceability and replay. They do not prove who created the data, that a topology matches reality, or that the result is an engineering study.

## Contribution gate

Before accepting a new public fixture, a reviewer must answer **yes** to all of the following:

- Was the dataset created specifically for this repository?
- Can every number and timestamp be explained without referring to a real facility or confidential source?
- Are names, IDs, labels, and comments plainly fictional and free of customer identifiers?
- Does the fixture avoid addresses, coordinates, serial numbers, network details, SCADA/BMS tags, ticket IDs, and incident narratives?
- Is `data_classification` exactly `synthetic`?
- Are assumptions and limitations explicit?
- Are expected results independently calculated and covered by tests?
- Has the diff been checked for credentials, personal data, proprietary documents, and generated outputs?

If origin is uncertain, reject the contribution until clean-room provenance can be demonstrated.

## Private integrations

The public version 1 schema cannot receive real design data because it requires `data_classification=synthetic`. An organization may use the structural model as the basis for a separately governed private contract version, but it must use an honest classification and a parser that explicitly supports that new version. It must never relabel real data as synthetic. Such a private mapping requires its own data inventory, lawful basis, access controls, retention schedule, threat model, validation process, and qualified engineering review.

Do not open a pull request containing an organization's mapped snapshot, scenario, result, telemetry, screenshot, or diagnostic log. Reproduction cases for public issues must be rebuilt from scratch using fictional identifiers and values.

## Retention and deletion

The reference database stores run inputs and outputs for reproducibility and does not define a production retention promise. A production operator must set a justified retention period, restrict backups consistently, implement tested deletion procedures, and document any legal or audit hold. The safest public workflow is to run only bundled synthetic examples.
